# 青年集体婚礼编排

编排多人婚典礼序、婚书与影像授权，避免现场错配。

## 领域资料

`contracts/domain.schema.json` 规定共享资料结构，`fixtures/domain.json` 保存不含真实个人信息的示例。当前参与方包括新人、联合主办单位、现场礼仪团队、影像与婚书制作方。

资料所依据的领域事实如下：

- 活动有五十对青年人才参加
- 婚典包含巡游、多个古礼环节和集体诵读婚书
- 现场同时展示电子婚书与实体婚书

## 编排服务（src/orchestration.py）

`WeddingEvent` 是一场婚典的领域聚合，覆盖活动前编排、现场执行与活动后处置，
不依赖第三方库，也不持久化任何真实证件影像：

- **授权先行**：身份核验、公开展示、婚书制作、市集预约四类授权分开授予、分别撤回；
  身份核验只记录不透明的证件保管凭据（`id_doc_token`），不保存证件影像。
- **礼序精确对应**：巡游位置与入场位置原子更新；迟到跳序把整对新人顺延至队尾，
  并在原位留出空位标记，后续环节自动按新顺序执行。
- **变更向未执行环节传播**：撤回公开会让未播影像变为 suppress、素材撤下；
  替换素材只影响未播环节；双方取消会从所有未执行环节移除并取消未交付预约；
  设备故障先改道备用设备，全部不可用时把未播项顺延到下一个有屏环节。
- **已完成记录不可变**：环节执行时把当时的展示姓名、素材版本、婚书版本固化为快照；
  已播放影像、已签署交付的婚书保留原记录，后续姓名修订不会改写历史。
- **婚书版本一致门禁**：电子婚书发布后实体婚书才能付印；付印后姓名修订或授权撤回
  会作废旧版（实体 `void`、电子 `superseded`）并开出待重批草稿，电子与实体核对一致
  前执事岗只能看到 block/withhold，系统拒绝签署。
- **最小知情岗位视图**：巡游、大屏、入场、执礼、婚书执事、市集六类岗位只能在
  自己环节进行期间读取当前队列，且只拿到所需字段（无证件、礼服、联系方式）。
- **新人自查**：`person_preview` 让每位新人确认自己将如何被展示，并查看
  待执行环节、已完成记录和全部授权/修订变更。
- **负责人总览**：`director_view` 不暴露证件资料，可核对五十对的核验、授权、姓名、
  礼服、顺序、素材、婚书一致性、环节进度，以及活动后按期删除清单。
- **到期删除**：证件与公开/市集资料按授权保留期限（默认 30/30/90 天）清除；
  婚书授权无到期日，已签署婚书长期保留，删除动作本身写入审计日志。

## 本地校验

运行项目自带测试即可检查基础资料读取与编排规则：

```bash
python -m unittest discover -s tests -v
```

`tests/test_orchestration.py` 以三对新人的小规模婚典覆盖：完整流程、撤回公开、
素材替换前后留痕、迟到跳序、双方取消、设备故障改道与顺延、婚书重印门禁、
岗位最小视图、新人自查、负责人核对与活动后删除。仓库不保存账号、密钥、连接串或真实身份信息。
